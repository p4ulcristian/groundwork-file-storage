# The bucket through the AWS SDK for Java v2

> **Changed in part** by [A retry wait of 0 sends again at once](2026-10-27-a-retry-wait-of-0-sends-again-at-once.md) (2026-10-27): a wait of 0 is the SDK's `retryImmediately`.

> The user's decision, 2026-10-27 (keep groundwork minimal, but what a vetted library solves is solved with that library: crypto, tokens, request signing, protocols, parsers, formats; hand-written code that only saves a dependency is wrong). Since v0.2.1. Replaces [The bucket through the JDK's http client; SigV4 written by groundwork-file-storage](2026-10-26-the-bucket-through-the-jdks-http-client.md). Changes in part [A file on disk is stored streamed, never held whole](2026-10-26-a-file-on-disk-is-streamed-to-the-bucket.md) (what the bucket checks), [Secrets are safe's wrapped secrets](2026-10-23-secrets-are-safes-wrapped-secrets.md) (where the key is revealed) and [A deleted public file is purged from Cloudflare's cache](2026-10-26-a-deleted-public-file-is-purged-from-the-cache.md) (its client).

**Decision:** groundwork-file-storage talks to the bucket through the AWS SDK for Java v2 (`software.amazon.awssdk/s3` 2.57.4, on the SDK's `apache5-client`; its Netty client excluded): one `S3Client` and one `S3Presigner` per store. The hand-written SigV4 (`groundwork-file-storage.signing`), its S3 requests and XML reading, and AWS's SigV4 test vectors are deleted: none tested anything of ours.

- **The operations.** `PutObject` from `RequestBody.fromFile` (streamed, its known length) or `fromBytes`, with `If-None-Match: *` (412: there already); `GetObject` (404: nil), `DeleteObject`, `ListObjectsV2` (the SDK's paginator), `CopyObject` with `If-None-Match: *` and `MetadataDirective REPLACE` (an error inside its 200 read by the SDK). A failure is `:groundwork-file-storage/bucket-failed` with the SDK's status, error code and message.
- **R2's settings**, from R2's page for the SDK for Java v2: `endpointOverride` the settings' `:endpoint`; `pathStyleAccessEnabled(true)`; `chunkedEncodingEnabled(false)` (R2 answers aws-chunked puts 403); the settings' `:region` (R2: `"auto"`, which R2's compatibility page says is its region). `requestChecksumCalculation` and `responseChecksumValidation` `WHEN_REQUIRED`: the SDK's newer default puts a CRC32 of the whole object in an aws-chunked trailer, and R2's compatibility page takes CRC32 only as a composite (multipart) checksum. No `~/.aws` profile file is read.
- **What the bucket checks.** A put carries `Content-MD5`, the MD5 of the bytes hashed for its key, computed in the same read as the sha256 (R2 takes `Content-MD5` on `PutObject`): a file that changed between its hashing and its put is refused (`BadDigest`). Over https the SDK signs the request, not the payload (`UNSIGNED-PAYLOAD`); over plain http (a test bucket) it signs the payload too.
- **Timeouts and retries.** The settings' `:connect-timeout-ms` is the http client's connection timeout; `:request-timeout-ms` its socket timeout and the SDK's `apiCallAttemptTimeout` (one attempt: sending, then the answer). `:retries` is the SDK's `StandardRetryStrategy`: `maxAttempts` `:max-retries` + 1, `exponentialDelayWithoutJitter(:first-wait-ms, :max-wait-ms)` (the same waits as before), no circuit breaker, and only a 429, 503 or 504, or a request that never connected, is sent again, as before. The SDK's http client never follows a redirect.
- **Signed links** are S3Presigner's GET, with `responseContentDisposition` for `:download-as`. S3Presigner signs at the moment it is called and takes no clock, so a link's request carries a presigner of its own (its `overrideConfiguration().signer`, which S3Presigner calls in place of its own signing): it signs the request S3Presigner made with the SDK's `AwsV4HttpSigner`, in the query string, with S3Presigner's own properties (no payload, no path normalizing, no double encoding) and a fixed clock at the link's moment: now for `[:from-now s]`, the window's start for `[:window s]`. Every link to a file made within one window is the same address.
- **The key** is revealed by a credentials provider of groundwork-file-storage's, which the SDK asks each time it signs a request or a link; the settings never hand the SDK the key itself.
- **The cache purge** keeps a JDK `HttpClient` of its own (one POST to Cloudflare's REST api, its JSON by jsonista, the same retry rule): a REST call, not a protocol.

**Why:** SigV4, S3's requests and its XML answers are a protocol with its own corner cases (path encoding, canonical requests, presigning, 200 answers with errors); the AWS SDK is AWS's own implementation, which R2 documents. It streams a put from a file, which aws-api did not, the reason v0.2.0 wrote its own.

**The price:** a far larger dependency (the SDK's core, S3, its XML protocol, Apache HttpClient 5) for six operations. The SDK's own defaults apply where the settings say nothing, and are not settings: the http client's pool (50 connections, a connection waited for at most 10 s, idle ones closed after 60 s), `Expect: 100-continue` on puts, the SDK's user agent. Content-MD5 adds a second digest to the read that hashes a file. A link's presigner uses the SDK's `Signer` and `Presigner` interfaces, which the SDK marks deprecated; the request override that takes it is not.

**Instead of:**
- **v0.2.0's own SigV4 and S3 client:** a protocol read by nobody else; a test suite that proved only the signer
- **the SDK's payload signing over https, its sha256 in `x-amz-content-sha256`:** the SDK hashes the file itself, when it sends it, so a file that changed after groundwork-file-storage hashed it would be stored under the old content's key; and a third read of the file
- **`x-amz-checksum-sha256`:** R2 takes SHA-256 only as a composite (multipart) checksum
- **the SDK's async client (Netty) or its CRT client:** a second http stack, or native code, for calls that are synchronous here
- **one S3Presigner per window:** S3Presigner signs at the moment of the call either way
